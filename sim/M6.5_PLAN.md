# M6.5 計畫 v1.0：feishu_bot ↔ advisor MatchEngine state 一致性

> 預估：1–3 個工作日
> 目標：消除 sim 模擬盤目前 commands.py（飛書手動下單）跟 sim/advisor（Claude 自動下單）兩條路徑的 MatchEngine state 不同步問題 — 兩個 process 看到的 cash / positions / total_realized_pnl 可能完全不一致，造成「飛書 /portfolio 顯示空持倉、advisor 看到 200 股、fills.jsonl 真實累計 100 股」這種三方歧異。
> 完成標準：commands.py 跟 advisor 路徑對同一份 fills.jsonl 做寫入後，無論 bot 是否重啟、advisor 是否自然觸發、dispatch 是否清掃，所有讀者拿到的 account state 100% 一致；既有 M1–M6 全綠零回歸；新增 ≥6 個 cross-process consistency 整合測試。

---

## Context（為什麼現在要做）

- M6 階段二（2026-05-06）部署 advisor launchd 後**首次踩到**這個問題：
  - advisor 進程 5/6 寫進 orders.jsonl 的 34 筆訂單孤立、feishu_bot 進程內 MatchEngine 看不到（M6.1 已用 post-submit match + dispatch CLI 補撮合）
  - 但 M6.1 只解了「撮合鏈路」，**沒解「state 一致性」** — 兩個 process 看到的帳戶仍可能不同
- 觸發發現的具體現象：
  - `scripts/feishu_bot.py:_ensure_sim_initialised`（line 110-145）：「**第一次有 sim 指令時 lazy init engine**」+ 「`bot 重啟資料歸零（M3 不做 replay）`」
  - `sim/advisor/runner.py:init_engine_from_fills`：「**每次 advisor 進程啟動都從 fills.jsonl replay 重建**」
  - 兩個 process 對同一份 fills.jsonl 採取相反策略
- 問題還沒爆是因為 W 5/6 沒在飛書下手動 `/sim` 指令。一旦有人下、bot lazy init 起來，問題會立刻顯化。

## 已確認的事實

| 路徑 | MatchEngine init 策略 | account 起始狀態 |
|---|---|---|
| `commands.py`（飛書手動）| feishu_bot lazy init，第一次 sim 指令觸發 | cash=1M, positions={}, realized_pnl=0（記憶體歸零，**不 replay fills.jsonl**） |
| `sim/advisor decide`（M6 launchd）| 每輪進程啟動 `init_engine_from_fills` | replay fills.jsonl 重建 cash/positions/realized_pnl |
| `sim/advisor dispatch`（M6.1 launchd）| 每輪進程啟動 `init_engine_with_pending` | replay fills + replay PENDING orders |
| `sim/advisor brief / metrics`（M6 launchd）| 不啟 engine，純讀 fills/orders/equity_curve 聚合 | N/A |

不一致場景示例：

1. 早上 09:01 W 在飛書下 `/sim buy 2330 100 MKT` → feishu_bot lazy init engine、撮合 → fills.jsonl +1 筆 → bot 內 MatchEngine 持倉 2330 100 股、cash 減
2. 09:05 advisor decide 進程啟動 → init_engine_from_fills replay → 看到 100 股、cash 減 ✓ 跟 bot 一致
3. **下午 14:00 飛書 bot 因 debug 重啟** → 新 feishu_bot 進程啟動、MatchEngine 還沒 lazy init
4. 14:01 W 飛書 `/sim portfolio` → bot lazy init engine（**記憶體歸零，cash=1M, positions={}**）→ 顯示「無持倉、cash 100 萬」
5. 14:05 advisor decide 進程啟動 → replay fills → 看到 100 股 + cash 減 → 跟 bot 完全不同步
6. W 在飛書下單 `/sim sell 2330 100`：bot 拒絕（持倉 0 不夠賣）；advisor 同時可能看到持倉 100 試圖加碼

## 設計決策

> 規劃日期：2026-05-06（M6 階段二 advisor launchd 部署當日，首次踩到 feishu_bot ↔ advisor cross-process MatchEngine state 不同步現象後展開）；W 同日拍板路線 2A + 3A + 4=是 + 5A + W6=不 block。

### 決策 1：fills.jsonl 是 source of truth（W 拍板：是）

不可能讓兩個 process 共享記憶體，唯一一致的是磁碟上的 jsonl 檔。所有路徑都把 fills.jsonl 當 ground truth，每次 init 時 replay。

替代方案是改架構走 daemon IPC（從天級工作量跳到週級），不採。

### 決策 2：feishu_bot 改 replay-on-init — 走 2A（lazy init 內 reuse `init_engine_from_fills`）

`scripts/feishu_bot.py:_ensure_sim_initialised` 內 init MatchEngine 後 reuse advisor 的 `init_engine_from_fills` 邏輯 replay，刪掉「記憶體歸零」warning。改動 ~20 行。

不採 2B（eager init + replay）：bot 啟動會慢，且無 sim 指令的 session 也吃 IO。
不採 2C（每次查詢前 replay）：重複工。

副作用：pytest fixture 重設 state 要對應改。目前 fills 才 4 筆毫秒級；半年後若累積到秒級 noticeable，再加 `--since YYYY-MM-DD` 截斷（推 M7）。

### 決策 3：撮合線程歸屬 — 走 3A（完全外移到 dispatch plist + commands.py single tick）

feishu_bot 不再起撮合 daemon thread（移除 `_SIM_RUNNER_STARTED`），撮合鏈統一靠 `com.w.sim-advisor-dispatch.plist` + commands.py / advisor submit 後立即 single tick match。bot 變單純：只負責收命令、查詢、通知。

不採 3B（兩條撮合線並存 + fcntl 檔案鎖）：跨進程鎖在 macOS 行為微妙，容易留坑。
不採 3C（移除 dispatch plist 維持 bot 內 thread）：advisor 進程下單後又孤立，退回 M6.1 前狀態。

**這是 M6.5 唯一高風險決定** — M3-M5 既有靠 bot daemon thread 的 e2e 測試要全部改 explicit `run_once(engine, feed)`，工作量最重。建議拆獨立 PR、跟測試遷移一起上，方便出事時單獨 revert。

### 決策 4：commands.py 對稱補強 single tick match（W 拍板：是）

3A 配套：commands.py 在 submit_order 後（飛書手動下單）跟 advisor 路徑一樣立即 single tick match 處理 MKT，否則 bot 飛書下 MKT 後「不立即看到成交」UX 崩。LMT/STOP/TP 仍交 dispatch plist 30 秒清掃，single tick + dispatch 互補不重疊。

### 決策 5：歷史 fills.jsonl — 走 5A（不動，含 4 筆 BUY 2330 持倉 400 股）

fills.jsonl 從 M1 累積到 M6（5/4-5/6）有 4 筆 BUY 2330（無對應 SELL）。M6.5 改完後 advisor / feishu_bot 都會 replay 這 4 筆 → 上線初始持倉 = 400 股 2330 + cash 對應減少。

不採 5B（移到 _archive 從空白起跑）：那 4 筆是真實測試交易，丟掉等於假裝沒發生、cash 1M 是假的。
不採 5C（加 `--since` flag）：工程量最大且現在沒急用。

**M6 驗收公式必須對應調整**：M6 「累積 PnL vs 0050」baseline 從含這 400 股 2330 的真實 cash 起算，不是 1M cash（W6 配套，不重起 20 日計時器）。

### 決策 6：M6.5 不 block M6 的 20 交易日驗收（W6 拍板：不 block）

M6 從 2026-05-07 起算照走，M6.5 並行做。M6.5 改 bot 端 + 撮合分工，advisor 決策邏輯零改動，唯一耦合是決策 5 的 baseline 數字。M6.5 上線當天起，M6 驗收以新 baseline 接續累積。

## 風險與不確定點

1. **改 feishu_bot 啟動行為**會影響飛書手動下單 UX：bot 啟動慢（要 replay fills），如果 fills 累積很多會 noticeable。M6.5 上線時 fills 才 4 筆、毫秒級；半年後可能十秒級，需要決策 5C 截斷機制。
2. **移除 bot 內撮合 thread 是大改動**：M3-M5 既有 e2e 測試多數依賴這條 thread。改完要重跑既有 233+11 = 244 全測 + 新增 6 個跨進程測試。
3. **commands.py + advisor 都做 single tick match 後，dispatch plist 還要嗎？** 答：要 — single tick 只處理本輪 submit 的訂單，跨輪 LMT/STOP/TP 仍需 dispatch 巡掃。dispatch + single tick 是互補不重疊。
4. **race condition**：dispatch plist 30 秒一輪 vs commands.py 即時下單 single tick，兩者讀寫 orders.jsonl 可能在毫秒級交錯。OS-level append 是 atomic 但「先讀全檔再決定 status」的邏輯不是。需要評估是否要加檔案鎖（決策 3B 的方案）— 但 30 秒 vs 毫秒下單，撞機率極低，先不加。
5. **initial_cash 處理**：replay 重建 cash 用 `initial_cash + cash_delta`，但 `initial_cash` 從 sim_config.yaml 讀。如果 W 中途改 initial_cash 配置，replay 結果會跳變。需要在 fills.jsonl 第一筆同時記錄當時的 initial_cash？或者 replay 看到 fills 第一筆時 lock 住 initial_cash？（M6.5 範疇，但 W6 拍板可推 M7）
6. **decision 9 daily_brief 不受影響**：純讀 fills + advisor_audit + equity_curve，state 一致性問題對它沒影響（它本來就不持有 engine state）。
